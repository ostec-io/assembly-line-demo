# Assembly Line Demo

**One file in. One application out.**

This repository contains the complete output of a single file drop through an [AgentFlow](https://ostec.io) cognitive orchestration pipeline.

A product requirements document was dropped into a watched folder. The PRD itself was generated by ChatGPT — a random fake product brief for a deep work app called FocusFlow. No editing, no tailoring, no special formatting for the pipeline. Just a generic PRD dropped into a folder.

No editor was opened. No prompt was written. A three-station assembly line processed it autonomously and produced a fully structured Spring Boot application.

---

## What happened

| Stage | Agent | Input | Output | Time |
|-------|-------|-------|--------|------|
| **Station 1** | DDD Specialist | Raw PRD (380 lines) | Domain-Driven Design specification — 8 subdomains, 7 bounded contexts | ~8 min |
| **Station 2** | Component Architect | DDD specification | Spring Boot component outline — documents, repositories, services, controllers, DTOs, events per context | ~5 min |
| **Station 3** | Code Foreman | Component outline | 24 sequential implementation tasks across 7 bounded contexts, assigned to a code worker agent | ~12 min |
| **Execution** | Code Worker | 24 task briefings | 200 Java files, 19,076 lines of code | ~2.5 hrs |

Total elapsed time from file drop to complete application: **approximately 3 hours.**

Zero human intervention after the trigger.

## The pipeline

Each station receives **only the output of the previous station** — not the raw PRD, not the full conversation history. This is structured context handoff, the same principle that makes manufacturing assembly lines work.

**Station 1: Domain-Driven Design**
The DDD specialist reads the PRD and produces a formal domain model. It identifies core, supporting, and generic subdomains. It defines bounded contexts with aggregates, domain events, application services, and repository contracts.

**Station 2: Component Architecture**
The component architect reads the DDD spec and translates it into a concrete Spring Boot component outline. Every class, interface, and method signature is specified — per bounded context.

**Station 3: Code Foreman**
The foreman reads the component outline, classifies the project scope (this one was classified as LARGE), and decomposes it into ordered implementation tasks. Documents and repositories first, then services and events, then controllers and DTOs — per bounded context. It creates a sprint with dependency ordering and assigns everything to a code worker.

**Execution**
The code worker picks up each task in sequence, building on the foundations laid by earlier tasks. All 24 completed without failure.

## What this demonstrates

The assembly line pattern — trigger, decompose, specialise, orchestrate, output — is built from general-purpose primitives. The agents carry the domain expertise. The platform carries the orchestration.

Nothing in the pipeline knows it's building software.

## Bounded contexts

The generated application covers 7 bounded contexts from the FocusFlow PRD:

1. **Session Execution** — Deep work session lifecycle (create, start, check-in, interrupt, complete, abort)
2. **Accountability** — Live focus rooms with participants, goals, locking, and result reveals
3. **Performance** — Daily scoring, weekly analytics, streak tracking, focus score calculation
4. **AI Planning** — Session plan generation, editing, versioning, learning memory
5. **Entitlement & Billing** — Subscription management, usage quotas, Stripe webhook processing
6. **Identity & Access** — User profile shadows, Keycloak sync, auth session auditing
7. **Insights & Reporting** — Analytics ingestion, KPI computation, conversion dashboards

Each context follows the same layered structure: documents → repositories → services → controllers → DTOs → mappers → events.

## Conventions

The generated code follows these conventions throughout:

- Java 21, Spring Boot 3.3.x, MongoDB
- `tenantId` and `orgId` isolation on every write and repository query
- `@PreAuthorize` on every endpoint
- Domain event publishing via outbox pattern
- No Lombok `@Data` (explicit getters/setters)
- Structured audit trails
- Cross-context communication via event listeners and saga orchestrators

---

## Limitations

This is generated output, not a production-ready application. It has not been compiled, tested, or integrated, and the repository contains no tests. It represents the structured starting point that the assembly line produces — consistently patterned and ready for human review and refinement.

The value isn't in any single generated file. It's in the system that coordinated 24 tasks across 7 bounded contexts from a single input document.
